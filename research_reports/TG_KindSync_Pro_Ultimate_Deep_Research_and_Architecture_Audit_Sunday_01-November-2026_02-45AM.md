### 1. Cryptographic HMAC-SHA256 Verification Details
In compliance with the official Telegram Bot API specification (section *Validating data received via the Mini App*):
1. The Telegram Mini App client extracts `window.Telegram.WebApp.initData`, a URL-encoded string containing `query_id`, `user` (JSON string), `auth_date`, and `hash`.
2. The server parses the query string into key-value pairs, extracts `hash`, and removes it.
3. The remaining keys are sorted alphabetically and joined with newlines in the format `key=value\n`.
4. A SHA-256 HMAC secret key is derived from the bot token:
   $$\text{SecretKey} = \text{HMAC-SHA256}(\text{"WebAppData"}, \text{DEVI\_TELEGRAM\_BOT\_TOKEN})$$
5. The signature is computed and compared:
   $$\text{ComputedHash} = \text{HMAC-SHA256}(\text{SecretKey}, \text{DataCheckString})$$
   $$\text{Verified} = \text{hmac.compare\_digest}(\text{ComputedHash}, \text{ReceivedHash})$$
6. Only if verified does the server decode `user.id`. If `user.id` $\notin \{1553619403, 759038032\}$, access is immediately denied.

### Invariant Equations
Let $\mathcal{M} = \{m_1, m_2, \dots, m_n\}$ be the sequence of messages in the source channel with monotonic ordering $i < j \implies \text{seq}(m_i) < \text{seq}(m_j)$.

1. **In-Order Fetching**:
   $$\forall i, \quad \text{fetch\_order}(m_i) = i$$
   The forwarder pulls messages using Telethon's `iter_messages(reverse=True)` or strictly ordered SQLite message IDs.
2. **Ticket Allocation**:
   Each message is assigned an immutable monotonic ticket $\tau(m_i) = i$ upon entering the pipeline.
3. **Commit Condition (MonotonicSequenceBarrier)**:
   A message $m_k$ can be dispatched to the destination channel if and only if:
   $$\text{dispatch}(m_k) \iff \tau(m_k) = \tau_{\text{expected}}$$
   Where:
   $$\tau_{\text{expected}}(t + 1) = \tau_{\text{expected}}(t) + 1$$
4. **Conclusion**:
   Even if network jitter causes a small text message ($m_{102}$) to finish downloading before a 3GB video ($m_{101}$), $m_{102}$ is parked inside the memory barrier. $m_{102}$ will **NEVER** be dispatched until $m_{101}$ is completely written to the target chat. **Zero desynchronization is mathematically guaranteed.**
